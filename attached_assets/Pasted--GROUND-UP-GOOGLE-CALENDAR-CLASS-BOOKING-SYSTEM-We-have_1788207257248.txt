# GROUND UP — GOOGLE CALENDAR CLASS BOOKING SYSTEM

We have completed a full audit of the existing Ground Up application.

We are now changing the booking architecture.

The goal is to replace the current fragmented combination of:

* static schedule data
* Calendly
* internal booking logic
* separate availability logic

with a simpler architecture built around:

# GOOGLE CALENDAR + GROUND UP BOOKING ENGINE

This task should focus specifically on the class booking system.

Do NOT redesign the entire website.
Do NOT rebuild unrelated portal features.
Do NOT publish automatically.

---

# 1. ARCHITECTURE DECISION

Ground Up will use:

## Google Calendar as the authoritative class schedule

Google Calendar determines:

* what classes exist
* class date
* start time
* end time
* instructor/calendar
* location
* cancellations
* schedule changes

Ground Up should synchronize those class events into the application.

## Ground Up as the authoritative reservation system

Ground Up determines:

* who booked
* capacity
* remaining spots
* waitlist
* member eligibility
* first-time visitor eligibility
* cancellation
* attendance
* no-show status
* booking history

Do NOT attempt to store participant capacity or reservation truth only inside Google Calendar.

---

# 2. CALENDLY TRANSITION

Calendly should no longer be the normal booking system for Ground Up classes.

Do NOT delete the integration immediately.

Instead:

1. inventory current Calendly dependencies;
2. preserve existing historical Calendly IDs and bookings;
3. implement Google Calendar synchronization;
4. implement Ground Up reservations against synchronized class events;
5. validate the new system;
6. remove standard-class Calendly CTAs;
7. retain Calendly only if Ground Up still wants it for private appointments or consultations.

Do not destroy historical evidence.

---

# 3. GOOGLE CALENDAR CONNECTION

Use a secure Google Calendar integration.

Do not hard-code access tokens or credentials.

Determine the correct Google authentication model for the existing Replit environment.

The integration must support secure refresh/token handling where required.

Do not expose Google credentials to the browser.

All Google Calendar API access must occur server-side.

---

# 4. CALENDAR STRATEGY

Prefer a dedicated Google Calendar for Ground Up classes.

Example concept:

**Ground Up Classes**

This avoids mixing:

* personal appointments
* staff meetings
* private calendar events
* unrelated business events

with public class schedules.

If multiple instructor calendars are required later, architect cleanly for that possibility.

For the initial implementation, one dedicated Ground Up Classes calendar is preferred unless the existing operational setup clearly requires multiple calendars.

---

# 5. GOOGLE EVENT → GROUND UP CLASS

Each relevant Google Calendar event should synchronize into a local Ground Up class occurrence.

Ground Up needs a local representation of the event.

Store appropriate fields such as:

* Google event ID
* Google calendar ID
* title
* description
* start date/time
* end date/time
* location
* instructor reference if known
* status
* updated timestamp
* Google sync timestamp
* Ground Up capacity
* Ground Up class type
* first-visit eligibility
* booking enabled
* audience/eligibility
* synchronization state

Google's event ID must remain stable for reconciliation.

Do not duplicate the same Google event on every sync.

---

# 6. SOURCE-OF-TRUTH RULES

The system must have explicit ownership rules.

## Google owns

* class date
* class start time
* class end time
* class title where appropriate
* class cancellation/deletion
* calendar event changes
* basic location

## Ground Up owns

* reservations
* capacity
* waitlist
* attendance
* membership eligibility
* first-visit eligibility
* participant status
* booking status
* internal class metadata not appropriate for Google Calendar

Document any exceptions.

Avoid two-way ownership of the same field unless absolutely necessary.

---

# 7. SYNCHRONIZATION

Implement reliable synchronization between Google Calendar and Ground Up.

The application must be able to detect:

* new class
* changed class
* cancelled/deleted class
* changed time
* changed location

Synchronization should be idempotent.

Repeated synchronization must not create duplicate class occurrences.

Track:

* last successful sync
* last attempted sync
* sync failure
* event-specific error where relevant

---

# 8. SYNC STRATEGY

Use the most reliable architecture supported by the current environment.

Possible approaches include:

* periodic synchronization
* Google push notifications/webhooks
* incremental sync tokens

Prefer Google's incremental synchronization model where practical.

If webhook/push notification complexity makes the first phase fragile, it is acceptable to use a reliable scheduled sync initially.

Do not pretend real-time synchronization exists if it does not.

Document expected synchronization delay.

---

# 9. FAILURE BEHAVIOR

A Google API failure must NOT erase the existing Ground Up schedule.

If synchronization fails:

* preserve last-known valid class data;
* mark synchronization health appropriately;
* log operational error;
* allow admin to see sync status;
* do not silently empty the schedule.

Fail safely.

Ground Up is located in Oxnard, California.

Standardize all booking behavior around:

**America/Los_Angeles**

Fix the existing America/New_York configuration drift found in the audit.

Google event timestamps must be interpreted correctly.

Store timestamps consistently and render them in Pacific Time for Ground Up users.

Test daylight-saving transitions.

# 21. CAPACITY

Capacity is NOT controlled by Google Calendar attendee counts.

Ground Up must enforce class capacity.

Example:

capacity = 6

Ground Up confirmed reservations:

6

Result:

class full

The seventh user should not become confirmed.

Implement atomic server-side protection.

Two simultaneous users attempting to book the final spot must not both succeed.

---

# 22. GOOGLE EVENT ATTENDEES

Do NOT automatically add every Ground Up participant as a Google Calendar attendee unless there is a strong operational reason.

This could:

* expose participant emails
* cause Google invitation emails
* create privacy problems
* clutter calendars
* make Google attendees look like reservation truth

Ground Up should retain the authoritative participant roster internally.

If later we explicitly choose to add attendees, make it an intentional opt-in architecture.

For this phase:

**Do not use Google attendee lists as the booking roster.**
